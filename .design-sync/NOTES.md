# design-sync notes — @biddaloy/ui → Claude Design

## Repo quirks

- **No build script.** `ui/package.json`'s `main`/`types`/`exports['.']` all
  point directly at `./src/index.ts` — the package is deliberately
  "consumed as source" by every SPA (see `ui/README.md`). `cfg.entry` is
  `./ui/src/index.ts`; the converter bundles straight from TS source
  (esbuild's synth-entry mode). No `buildCmd` needed or set.
- **`cfg.tsconfig` deliberately NOT set.** `ui/tsconfig.json`'s
  `@biddaloy/shared` path alias (`["../shared/src"]`, a bare directory, no
  `/index.ts`) breaks esbuild's tsconfig-paths substitution — it doesn't
  append the implicit index file the way Node's own resolver does, so
  `@biddaloy/shared` failed to resolve once tsconfig was wired up. Nothing
  in `ui/src` actually uses the `@/*` alias (checked: zero matches), and
  `@biddaloy/shared` already resolves fine via the normal yarn-workspace
  `node_modules` symlink. If a future component genuinely needs `@/`
  aliases, this will need revisiting (maybe `componentSrcMap`-level
  per-file handling instead of the blanket tsconfig field).
- **`cfg.cssEntry` points at a generated file, not a committed one.**
  `ui` ships no static compiled CSS (Tailwind v4's utility generation
  happens per-consuming-app via `@tailwindcss/vite`, not in `ui/` itself).
  The storybook-CSS-fallback scraper (`css-fallback.mjs`) also couldn't
  find it: this repo's Storybook build (Vite) doesn't emit a static
  `<link rel="stylesheet">` in `iframe.html`'s source — the CSS loads via
  a JS-injected `<style>` at runtime instead, which the scraper's static
  HTML parse can't see. Fix: `ui/.design-sync-compiled.css` is a **scratch
  copy** of the real compiled CSS pulled straight out of
  `.design-sync/sb-reference/assets/preview-*.css` after building the
  reference storybook — gitignored, regenerated by every sync (see
  `.gitignore`'s "design-sync" section). Run `yarn design-sync:css`
  (from `ui/`) before a sync on a clean checkout — it builds the
  reference storybook and copies the asset in one step
  (`scripts/sync-design-css.mjs`), and fails loudly instead of leaving
  `cssEntry` pointing at nothing if the expected asset is missing or
  ambiguous. **Re-sync risk**: if a future Tailwind/Storybook upgrade
  changes how the CSS loads, re-verify this copy step still finds the
  right asset file (the hash in the filename changes every build; the
  script matches by `preview-*.css` prefix, not a fixed filename, and
  fails rather than guessing if zero or more than one match).
- **`@storybook/addon-a11y` was pinned to `^10`** while every sibling
  `@storybook/*` package was `^8` — broke `storybook build` outright
  (`storybook/manager-api` etc. don't exist until Storybook v9+ unified the
  `storybook` package). Fixed to `^8` to match; this is a real, standalone
  bug independent of design-sync (confirmed `yarn workspace @biddaloy/ui
build-storybook` failed identically before the fix) — not something a
  future re-sync needs to redo, since it's now committed in
  `ui/package.json`.
- **`cfg.provider` is `{"component": "I18nProvider"}` only** — no
  `QueryClientProvider`. `probe.mjs`'s auto-detection returned a minified
  `Vi` symbol (not a real, usable component reference — discarded).
  `I18nProvider` is what most stories actually need (Suspense-gated
  `useTranslation()`); only one story anywhere in the roster
  (`Placeholder`'s `MswBackedData`) needed live query data, and that
  component is excluded entirely (see below). If a future component's
  story genuinely needs `QueryClientProvider`, this will need a nested
  `cfg.provider.inner` — none of the 28 synced components hit that yet.
- **`Placeholder` excluded** (`titleMap: {"Placeholder": null}` — the
  storybook-shape exclusion mechanism keys off the _derived component
  name_ — `titleParts()` in `lib/common.mjs` takes the title's last
  segment matching a known export, e.g. `"Infra/Placeholder"` →
  `"Placeholder"`, not the full title string — not `componentSrcMap`,
  which is package-shape's own knob and has no effect on a
  storybook-driven component roster).
  Its own file header says it explicitly: "Temporary stand-in for
  [8.1.4]'s scaffold check... Delete this file and its export once
  [8.1.3] lands a real component." It's not a real design-system
  component — it exists only to prove the import-boundary worked before
  any real wrapper existed, and one of its stories (`MswBackedData`)
  calls `useStudents()`, which needs a `QueryClientProvider` this sync
  doesn't wire up. Excluding it (rather than skipping just that one
  story) is deliberate: nothing about this component belongs in a design
  agent's component library. **Re-sync risk**: once a real component
  replaces it and `placeholder.tsx`/`.stories.tsx` are actually deleted
  from the repo (per that file's own comment), this exclusion becomes a
  no-op and can be removed from config — not urgent, just cleanup.
- **`Dialog`/`Menu`/`Tooltip` set to `cardMode: "single"`** —
  `[GRID_OVERFLOW]` flagged all three: their stories render into
  `position: fixed`/portal content (Radix's own portal-to-`document.body`
  behavior) that a grid cell can't visually contain. Standard,
  expected fix for any overlay/portal component per the skill's own
  decision tree — not a fidelity gap.
- **`LocaleSwitcher` `[RENDER_THIN]` is a false positive, accepted.**
  The heuristic checks for text content; `LocaleSwitcher`'s trigger is
  deliberately icon-only (`<Button iconOnly aria-label="Change
language"><LanguagesIcon /></Button>` — see the component's own doc
  comment on why). Confirmed visually via
  `ds-bundle/_screenshots/components__LocaleSwitcher.png`: all three
  stories (Default/Open/RTL) render the icon trigger correctly. `Open`
  and `Default` look identical in the static capture because this
  converter captures a static render per story, not the `play()`
  interaction (expected — see the storybook skill's own "capture harness,
  not interaction runner" framing). Nothing to fix; will read thin on
  every future sync too, permanently — not a regression to chase.

- **`[GENERAL]` play()-driven stories read as `close`, not `match`, and that's
  expected.** Several stories across this roster trigger their "interesting"
  state via a Storybook `play()` function (a button click revealing Zod
  validation, an open-menu interaction) rather than a controlled prop.
  Storybook's own reference build runs `play()` when a story loads; this
  converter's static per-story capture does not (by design — it's a render
  verification tool, not an interaction runner). The preview still renders
  correctly, just in its pre-interaction state, which is why these grade
  `close` with a note rather than `match` or `mismatch`. First hit:
  `FormField`'s `ErrorState`. Expect more of these across the roster (any
  story whose only path to its named state is a `play()` click) — this is
  not a bug to chase per-component, just the correct verdict for the shape.

- **`StatusBadge` ships as an unauthored floor card — accepted, diagnosed,
  not fixed this run.** Its preview module fails to compile with `!
preview build failed: StatusBadge: Cannot read file:
.../node_modules/postcss/lib/terminal-highlight
(node_modules/postcss/lib/css-syntax-error.js:5:32)`. Diagnosed down to:
  `status-badge.stories.tsx` is the **only** story file in this whole
  roster that imports `@biddaloy/shared` directly (confirmed via `grep -rl
"@biddaloy/shared" ui/src/**/*.stories.tsx` — one hit). Reproduced with a
  minimal owned preview importing nothing but `@biddaloy/shared`'s
  `FeeStatus` (no `StatusBadge` component, no icons, no story module) —
  same exact error. So this is specific to _this converter's preview-build
  plugin chain_ (`lib/story-imports.mjs` + friends, invoked only for
  per-component preview compiles, not the main `_ds_bundle.js` build,
  which resolves `@biddaloy/shared` fine — `permissions.ts` and
  `status-badge.tsx` both import it there without issue) reacting to
  something about resolving a workspace-symlinked package
  (`node_modules/@biddaloy/shared` → `shared/`) that no other component's
  preview ever touches. No `postcss.config.*` exists anywhere near
  `shared/`, so it isn't a real PostCSS invocation gone wrong — something
  in the plugin chain's own resolution/probing logic is what's actually
  failing to read that file, for reasons not yet root-caused past this
  point. **Deliberately not skipped** (`cfg.overrides.StatusBadge.skip`
  would leave an empty card — worse than the current floor card, which at
  least shows something). The component still ships fully functional
  (real `.d.ts`, real `.prompt.md`, callable from the bundle) — only the
  visual preview card is generic. Revisit if/when this pattern (a story
  file importing `@biddaloy/shared` directly) needs a real preview, or if
  someone wants to dig into `lib/story-imports.mjs`'s resolve hook for a
  workspace-symlink-specific fix.

## Re-sync risks

- `StatusBadge`'s floor card (see above) will keep recurring on every
  re-sync until the root cause is actually fixed — check whether a future
  `.ds-sync` update resolves it before re-diagnosing from scratch.
- The `.design-sync-compiled.css` copy step is scripted
  (`yarn design-sync:css`, see above) but still outside the standard
  converter flow — a re-sync must run it before the converter, or
  `cssEntry` will point at a stale/missing file. Worth eventually asking
  upstream whether `css-fallback.mjs` could special-case Vite's
  JS-injected-style pattern, since this is likely to recur for any
  Vite-based Storybook using Tailwind v4.
- `Placeholder`'s exclusion should be revisited once that file is actually
  deleted from the repo (see above).
- Storybook's `@storybook/addon-a11y` version pin (`^8`) should stay in
  sync with the rest of the `@storybook/*` devDependencies if this repo
  ever upgrades Storybook to v9/v10 — bump all of them together, not just
  the addon.
- **[GENERAL] A prior sync session pushed `_ds_sync.json` to the remote
  project without the content writes actually landing — the anchor
  vouched for 27 components the project didn't have.** Diagnosed
  2026-08-18: the local `ds-bundle/.resync-verdict.json` left behind by
  that session showed `capture.ok: false` with all 27 components in
  `pendingGrade` (`anchorUsed: false` — it never fetched the remote
  anchor via `--remote` either), yet the remote `_ds_sync.json` fetched
  via `DesignSync(get_file)` was byte-identical to that session's local
  one (same `bundleSha12`/`scriptsSha`) — meaning it got uploaded despite
  grading never completing. `DesignSync(list_files)` on the project
  showed only `ErrorState` + the `templates/sign-in/` mockup the whole
  time. Fixed by re-pushing the full local `ds-bundle/` (build + 26/27
  cached grades were still valid and matched the anchor's hashes exactly
  — no rebuild or re-grade needed) via the atomic-path sequence. **Watch
  for on future re-syncs:** always pass `--remote` to `resync.mjs`
  (§7 step 2) — never let a driver run finish an upload while
  `verification.pendingGrade` is non-empty, whatever the diff says.
- **`DesignSync(list_files)` is unreliable — treat it as a hint, not a
  source of truth.** After the repair above, three consecutive
  `list_files` calls each returned a different, incomplete subset of the
  project's actual files (missing the components/vendor/bundle files
  just uploaded, sometimes missing `README.md`/`github.md` too), while
  `DesignSync(get_file)` on the same paths returned correct content every
  time. Verify uploads by spot-checking specific paths with `get_file`,
  not by trusting `list_files`'s completeness.
